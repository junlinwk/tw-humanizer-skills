# Preset: 技術文章

適用：技術部落格、工程文章、API 介紹、實作經驗分享、系統設計討論

## 立場強度

**強**：技術文章一定要有判斷。讀者是來看你怎麼想的，不是來看百科全書。
- 明確說 X 方案比 Y 好，並給理由
- 明確說某個流行做法是錯的（如果你真的這樣覺得）
- 不要寫「兩種方案各有優劣」這種廢話

## 具體性要求

**最高**：每 300 字必須有以下其中之一：
- 程式碼片段（短的也行）
- 具體版本號（Node 18.2、Python 3.11、Postgres 14）
- 具體效能數字（p99 延遲、QPS、記憶體用量）
- 錯誤訊息原文
- 工具名 / 套件名 / 設定參數名

禁止：「效能提升」「大幅改善」「更快」這類無數字的概括。

## 第一人稱使用

**鼓勵**：「我試過」「我們團隊」「我踩過的坑」這類表述要積極使用。
技術文章如果沒有第一手經驗痕跡，就是 AI 味的溫床。

## 結構偏好

- 開頭：直接拋出問題或結論，不要鋪陳背景
- 中段：示範代碼 + 解釋。代碼比文字多沒問題
- 結尾：給 trade-off、或留待解問題。**不要**用「總結一下」開頭

## 額外禁用（技術文章常見的 AI 味）

詞語：
- 「賦能開發者」「提升開發體驗」「擁抱 X 技術」
- 「best practice」「state of the art」「cutting-edge」
- 「無縫整合」「開箱即用」「強大的」

句式：
- 「在進行 X 之前，讓我們先了解 Y」
- 「現在，讓我們看看 X」
- 「總結來說，X 是一個強大的工具」
- 「希望這篇文章對你有幫助」（結尾廢話）

## 鼓勵的寫法

- 「我花了三小時才發現是 timezone 的問題」
- 「這方案在小流量下能跑，但 5k QPS 就崩了」
- 「文件說會這樣做，實際上 v3.2 之後改了，我被坑過一次」
- 「不要用 X，用 Y。理由：[具體三點]」

## 範例對照

❌ AI 味
> Redis 是一個強大的記憶體資料庫，廣泛應用於快取和訊息佇列場景。其卓越的效能和豐富的資料結構使其成為現代應用架構的重要組成部分。

✅ 人寫
> Redis 7.0 的 functions 終於可以取代大部分 Lua script 的場景，但有個坑：FUNCTION LOAD 在 cluster mode 下不會自動同步到所有節點，要自己呼叫每個節點。我們上 prod 第一天就因為這個 cache miss 了 20 分鐘。
